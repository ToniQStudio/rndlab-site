# AGENTS.md — rndlab-site

Правила для ИИ-агентов и людей, которые работают с этим репозиторием.
Источник истины по ревью — `REVIEW.md`. При конфликте этих файлов с прямой
задачей пользователя приоритет у задачи, но о конфликте нужно сообщить.

## Что это за проект

Одностраничный сайт компании «РНД Лаб» (rndlab.ru): разработка, нейросети, данные.
Один HTML-файл без сборки, фреймворков и бэкенда. Язык интерфейса — русский.

## Структура

```
index.html                 весь сайт: HTML + <style> + один <script> в конце
assets/                    логотипы, иконки, клиентские SVG, видео, постер
scripts/check-links.mjs    проверка локальных ссылок и ассетов
REVIEW.md                  чек-лист ревью (обязателен перед PR)
.github/workflows/ci.yml   HTML-валидация, ссылки, pa11y, Lighthouse
```

Ключевые блоки `index.html`: `header.hdr` → `main.hero` → `.services`
(внутри `.expertise` и `.projects`) → `.about__base` (футер) → `#request-modal`.

## Запуск и проверки

Сайт статический: достаточно открыть `index.html` или выполнить `npm run serve`
(поднимает `python3 -m http.server 8080`).

```bash
npm install          # один раз
npm run check        # html-validate + проверка ссылок (обязательно перед PR)
npm run check:a11y   # pa11y: сам поднимает сервер (консультативно)
npm run check:lighthouse  # Lighthouse CI (консультативно)
```

В OpenCode перед PR: `/review` и `/security-review`.

## Жёсткие правила

- **Не переформатировать файл целиком.** Никаких «заодно поправил отступы»:
  diff должен быть минимальным и обозримым.
- **Не менять визуал и тайминги анимаций** без явной задачи. Скролл-сценарий
  hero/services/projects завязан на конкретные значения в JS — правка одного
  числа ломает последовательность.
- **Не добавлять сборку, фреймворки и зависимости.** Проект сознательно
  остаётся одним HTML-файлом. `devDependencies` — только инструменты проверки.
- **Не менять тексты, alt и типографику** без задачи: в текстах используются
  `&nbsp;`, «ёлочки», ручные `<br>` под макет. Сохранять как есть.
- **Не трогать `assets/`** без необходимости. Новые файлы — с объяснением веса
  и формата (webp/avif/svg).
- Не коммитить `node_modules/`, `.lighthouseci/`, `.DS_Store`.
- Не хранить в репозитории секреты, токены и ключи аналитики.
- Не пушить напрямую в `main` при наличии незакоммиченных правок: сначала
  ветка, потом PR.

## Известные дефекты (не исправлять без отдельной задачи)

Это осознанно отложенные этапы. Если задача их не касается — не трогай,
но упомяни в отчёте, если изменение делает хуже.

1. Форма заявки — заглушка: `submit` отменяется, показывается «Спасибо»,
   данные никуда не уходят.
2. Ссылка «Политика обработки данных» ведёт на `#`.
3. Нет аналитики (Метрика/GA) и целей.
4. Нет SEO-меты: `og:`, `twitter:`, `canonical`, `robots.txt`, `sitemap.xml`,
   JSON-LD.
5. Видео hero ~3.6 МБ (бюджет — 2.5 МБ), футер-видео ~1.5 МБ.
6. `aria-hidden` на модалке, блоке `.services` и футере `.about__base` при
   фокусируемых элементах внутри (ссылки проектов, кнопка «Наверх», поля формы);
   в модалке нет focus trap. html-validate показывает это как warning.
7. Деплой в репозитории не описан (нет конфига публикации) — уточнять у владельца.

## Уровни риска изменений

- **Красная зона — обязательна ручная проверка человеком:**
  форма и обработка персональных данных, политика/согласия, аналитика,
  SEO-мета, CI, `.gitignore`, деплой, любые внешние скрипты.
- **Жёлтая зона — ИИ-ревью + прогон проверок:** CSS, адаптив, скролл-логика,
  доступность, ассеты.
- **Зелёная зона — достаточно ИИ-ревью:** тексты, alt, мелкие правки разметки.

## Процесс

1. Ветка от `main` (`feat/...`, `fix/...`, `chore/...`).
2. Правки + `npm run check`.
3. `/review` и `/security-review`, замечания P0/P1 — исправить.
4. PR: что изменено, зачем, как проверено, скриншот/описание для визуальных правок.
5. CI должен быть зелёным. Job'ы `a11y` и `lighthouse` пока консультативные
   (`continue-on-error`) — их падение не блокирует мерж, но игнорировать
   систематические ошибки нельзя.
6. Красная зона — отдельный коммит и явное упоминание в PR, чтобы человек
   проверил вручную.

## Откат

Перед рискованным изменением — тег: `git tag pre-<что-меняем>`.
Откат: `git revert <sha>` (не `reset --hard` в общей ветке).

## Готово, когда

- `npm run check` проходит без ошибок;
- новых warning'ов в html-validate не появилось (или они объяснены в PR);
- `/review` не нашёл P0/P1;
- diff не содержит посторонних правок и переформатирования.
