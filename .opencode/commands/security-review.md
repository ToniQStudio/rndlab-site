Проведи security-ревью изменений в проекте rndlab-site.

Область: $ARGUMENTS
Если аргумент пуст — текущая ветка относительно `main` плюс незакоммиченные правки.

Собери контекст:

!`git status --short; echo '--- stat vs main ---'; git diff main...HEAD --stat 2>/dev/null || echo 'ветки main нет'; echo '--- package.json ---'; cat package.json`

Что проверить (в порядке приоритета):

1. **Персональные данные.** Что собирает форма (`name`, `contact`, `task`), куда
   уходят значения, есть ли обязательное согласие и рабочая ссылка на политику.
   Данные не должны попадать в URL, `localStorage`, логи, `console` или третьи
   стороны без явного решения владельца.
2. **DOM-XSS.** Найди все `innerHTML`, `insertAdjacentHTML`, `document.write`,
   `eval`, `new Function`, вставку через шаблонные строки. Проверь, есть ли путь
   от пользовательского ввода или `location.hash/search` к этим вызовам.
3. **Внешние ресурсы.** Скрипты, шрифты, iframe, пиксели, CDN. Требования:
   `https`, для сторонних скриптов `integrity` + `crossorigin`, минимум доменов,
   никаких скриптов без явного согласования.
4. **Ссылки.** `target="_blank"` без `rel="noopener noreferrer"`, `javascript:`
   URL, открытые редиректы, ссылки на `http://`.
5. **Секреты.** Ключи, токены, приватные эндпоинты в коде, конфигах, `.github/`.
   При подозрении на утечку в истории — `git log -p -S'<фрагмент>'`.
6. **Заголовки безопасности.** Для статики они задаются хостингом: CSP, HSTS,
   `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`.
   Если PR добавляет внешний ресурс — отметь, потребует ли это ослабить CSP.
7. **Зависимости.** `npm audit --omit=dev`; devDependencies не должны попадать
   в прод-артефакт. Новые зависимости — обоснованы ли.
8. **CI.** Workflow не печатает секреты, стоит `permissions: contents: read`,
   сторонние actions закреплены, shell-блоки не подставляют ввод пользователя.

Правила:

- Ничего не редактируй. Только отчёт.
- Для каждой находки: severity (P0/P1/P2), `файл:строка`, сценарий
  эксплуатации или утечки, конкретное исправление.
- Если риск теоретический и требует особых условий — так и напиши, не нагнетай.
- Отдельным блоком: «нужна ручная проверка» — что смотреть на хостинге,
  в проде, в реальной отправке формы.

Формат ответа:

```
## Итог
<можно ли мержить с точки зрения безопасности>

## P0
- `файл:строка` — риск, сценарий, исправление.

## P1
- ...

## P2
- ...

## Нужна ручная проверка
- ...

## Проверки
- `npm run check` — ...
- `npm audit --omit=dev` — ...
```
