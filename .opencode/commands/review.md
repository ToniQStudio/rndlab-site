Проведи ревью изменений в проекте rndlab-site по чек-листу `REVIEW.md`.

Что ревьюить: $ARGUMENTS
Если аргумент пуст — все изменения текущей ветки относительно `main`
плюс незакоммиченные правки.

Собери контекст:

!`git branch --show-current; echo '--- status ---'; git status --short; echo '--- stat vs main ---'; git diff main...HEAD --stat 2>/dev/null || echo 'ветки main нет — сравнивай с последним коммитом'; echo '--- stat worktree ---'; git diff HEAD --stat`

Порядок работы:

1. Прочитай `REVIEW.md` и `AGENTS.md` целиком — это правила проекта.
2. Определи объём: незакоммиченные правки → `git diff HEAD`; иначе коммиты
   ветки → `git log main..HEAD --oneline` и `git diff main...HEAD`; если пусто —
   последний коммит `git show HEAD`.
3. `index.html` читай участками целиком вокруг изменений. Инлайн-CSS, инлайн-JS,
   порядок блоков и скролл-сценарий связаны между собой — патч сам по себе
   не показывает последствий.
4. Пройди чек-лист по разделам. Не ограничивайся diff: проверь, не сломались ли
   якоря `#services/#expertise/#projects`, `id`, ссылки, пути к ассетам,
   вес файлов в `assets/`.
5. Запусти `npm run check` (валидация HTML + ссылки) и укажи результат в отчёте.
   При возможности — `npm run check:a11y` и `npm run check:lighthouse`,
   но их падение не считай блокером: они консультативные.

Ограничения:

- Ничего не редактируй и не форматируй. Только отчёт.
- Не выдумывай замечания: если пункт требует браузера, реального устройства
  или прода — пометь «нужна ручная проверка» и опиши, что именно проверить.
- Соблюдай severity: P0 — только реальные блокеры (потеря заявок, ПДн,
  безопасность, сломанная навигация). Стилистика — P2.

Формат ответа — как в `REVIEW.md`, раздел «Формат отчёта».
